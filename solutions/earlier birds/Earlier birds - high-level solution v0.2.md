## 1. High-level solution

Earlier Birds starts **Clawdia as soon as a new conversation is submitted in VetHub**, instead of waiting for UPM to lodge, check and request the assessment. VetHub becomes a **publisher of business events** on **Azure Service Bus** (already in use by VetHub and COS), and **Azure Functions** react to them. VetHub also works out the claim's **insurer routing context** before or during the eligibility check, so the right insurer environment is known from the start and later steps don't route again.

1. **VetHub publishes business events:** *Conversation Initiated*, *Insurer Routing Context Calculated*, *Conversation Completed*.
2. **Clawdia starts early.** A Function reacts to *Conversation Initiated* and starts a new Clawdia workflow instance, correlated by `conversationId`.
3. **COS no longer polls VetHub.** A Function reacts to *Conversation Completed* and calls a **new COS API that starts the claim from the conversation**, in the COS of the claim's insurer environment. As an MVP the request carries only the `conversationId`, and COS reuses the download part of today's polling mechanism to retrieve the claim (see COS-I-01 and §1.5).
4. **COS lodges directly.** With the routing context, COS knows which DAPI and UPM Dynamics API to call, so CLAPI *Claim Submission* / *Finish Claim Submission* (for this flow) and Dynamic CLAPI *Lodge Claim* are decommissioned.
5. **COS creates the CRN, publishes *Claim Initiated in COS* and calls the Clawdia workflow.** The call uses the `conversationId` as session id and carries the CRN, the policy number and, when the Durable Functions option is used, the insurer routing context. From then on the workflow is also correlated by CRN.
6. **Clawdia finishes early and waits.** Clawdia most likely completes the medical assessment before UPM asks for it. When UPM requests the assessment (Claw Init via Dynamic CLAPI, by CRN), Clawdia finds the waiting workflow and calls the *Write* API, as it does now.

**Result:** shorter assessment time, polling removed, extra API calls removed, event-driven architecture introduced, and the platform prepared for bigger changes.

### 1.3 High-level flow — to be

Same notation; events use the ArchiMate event shape and sit in the lane of the component that publishes them. New or changed functions are blue.

![Earlier Birds – to-be flow](<Earlier birds - diagram to be.png>)

What changes:

- **Clawdia moves from unit 20 to unit 2:** *Conversation Initiated* starts the workflow, and the assessment is ready at unit 9, long before UPM asks at unit 20. At that point Clawdia only finds the waiting workflow and writes.
- **Initiate conversation and Submit claim become events:** *Conversation Initiated* and *Conversation Completed*. *Conversation Completed* starts the claim in COS through the new API; the polling is gone.
- **One fewer layer for lodgement:** COS lodges directly in DAPI and the UPM Dynamics API using the routing context. CLAPI submission and Dynamic CLAPI *Lodge Claim* disappear from this flow.
- **UPM's checks, benefit, payment and the outcome to the vet are unchanged.**

### 1.4 Infrastructure required

A light-weight view for now, to be detailed with the component architecture.

- **Azure Service Bus:** existing namespaces (SYD and MEL, already used by VetHub and COS through NServiceBus). New topics for VetHub and COS business events, one subscription per handler.
- **Azure Functions:** event handlers for *Conversation Initiated* (start Clawdia) and *Conversation Completed* (call the COS start-claim API). If the routing context is handed over with Option 1 of §1.5, the second handler becomes a **Durable Functions** orchestrator, which needs its own storage (task hub).
- **Clawdia workflow correlations:** correlation is by `conversationId` first and by CRN once COS has generated it (OQ-04). **If the Clawdia runtime cannot correlate a waiting instance by these keys, a correlation repository (`conversationId`, CRN → workflow instance id) is needed.** Store and owner [TBC].
- **COS:** the new start-claim API is hosted in the existing COS API (IIS on Azure VMs), one per insurer environment (AU, NZ, VP).

### 1.5 Insurer routing context: hand-over to COS

*Insurer Routing Context Calculated* has no consumer yet. Two options are on the table; the choice is open (OQ-08).

| | Option 1 — Durable Functions orchestrator | Option 2 — context stored in VetHub |
|---|---|---|
| **How it works** | A Durable Functions orchestrator, keyed by `conversationId`, collects *Conversation Initiated* (new conversation id), *Insurer Routing Context Calculated* and *Conversation Completed*, then submits the request to the COS of the right insurer environment | VetHub saves the routing context on the conversation in its DB. COS reads it from VetHub when it retrieves the claim |
| **Request to COS** | `conversationId` and the routing context. Could also carry the VetXml data and the links to the attachments, so **COS no longer needs to read the VetHub DB** | Only the `conversationId` |
| **COS call into Clawdia** | `conversationId` (session id), CRN, policy number, routing context | `conversationId` (session id), CRN, policy number |
| **Consumer of *Insurer Routing Context Calculated*** | The orchestrator | None for now (event kept for future consumers) |
| **Pros** | Full decoupling of COS from VetHub's data; one place that knows when a conversation is ready | Smallest change; fits the MVP that reuses COS's download step |
| **Cons** | New stateful component (task hub, replay, versioning) | COS keeps reading VetHub's data; routing context not visible on the bus |

| # | Pattern | Where it is applied | Why | Watch-outs |
|---|---|---|---|---|
| AP-01 | Event-driven architecture with business events | VetHub and COS publish past-tense facts (*Conversation Initiated*, *Conversation Completed*, *Claim Initiated in COS*, …) | Producers don't need to know who reacts | Event contracts need an owner and versioning |

| AP-09 | Transactional outbox **[TBC]** | VetHub and COS publishing after a state change | No lost or phantom events | Needs a relay or framework support (NServiceBus outbox) |
| AP-10 | Schema-validated event contracts | Every published event | Service Bus does not enforce payload schemas | Event type and schema version as message properties; invalid messages to the DLQ |
| AP-11 | Strangler-style decommissioning | CLAPI submission (VPMS flow) and Dynamic CLAPI *Lodge Claim* | Switch callers first, retire after, with a rollback path | CLAPI has other consumers (*Impact*) |
| AP-12 | Speculative (eager) processing | Clawdia assesses before the claim is lodged | Takes the assessment off the critical path | ML and Logic App cost for abandoned conversations (§2.5); result may go stale if the claim changes |
| AP-13 | Correlated Process Inbox (candidate) | Future events reaching a waiting Clawdia instance (see `docs/correlated-process-inbox-pattern.md`, itself still under review) | One mailbox per business key, ordered, effectively-once | Not needed for the first increment |
| AP-14 | Event aggregator (Durable Functions orchestrator), candidate | Option 1 of §1.5: wait for the three VetHub events, then call COS | One place that knows when a conversation is complete | Stateful component to run and version |

#### Impact [TBC]

Findings from `docs/systems/COS/COS-summary.md` and `docs/systems/VetHub/VetHub-summary.md`. Consumers outside these repositories still need confirming (OQ-10).

- **CLAPI has other consumers** and can't be retired as a component: COS API (claim and policy queries), COS workers (ValidatePolicy via `api/Policy/Find`, SubmitClaims, attachment submission), COS AddAttachments Submit, the UPM Status Poller (`GetUpdatedClaimsList`, `GetClaimDetails`), VetHub.API (policy validation and GapOnly eligibility), Vet Partners (`api/External/*`) and CSP/other GoTech apps (*inferred*). Earlier Birds retires only the claim submission operations COS uses for the VPMS flow.
- **CLAPI routes by insurer** (`InsuranceProviderId`) to UPM+ DAPI AU/NZ, the Trupanion instance and Boomi for Vet Partners. If COS calls DAPI directly, the routing context must cover every target, including Boomi, or Vet Partners claims keep going through CLAPI.
- **The Claim Submission Saga is shared** by VPMS, CSP and partner claims: lodging directly from COS changes the saga for all channels unless it is switched by channel or insurer.
- **Attachments:** `api/Claims/Attachments` and `FinishSubmitClaim` are also used by the Claim Attachment Submission Saga, which is outside this flow.
- **Dynamic CLAPI *Lodge Claim*** (`PUT /api/Claims/Lodge/{claimId}`): the only caller found in the COS repositories is SubmitClaimAttachment (optional Dynamic Claims Lodge). Callers outside COS can't be determined from these repositories.
- **VetHub endpoint COS polls** (`GET api/Claim/NewConversations`): called by the COS VetHub Poller, one timer per insurer and one deployment per insurer environment (AU, NZ, VP). The download endpoints (`GET api/Claim/{id}`, attachments, `ConfirmDownload`) stay: the MVP reuses them.
- **Reverse dependency:** VetHub.Alert.StuckClaims reads the COS AU/NZ databases directly (`Claim.ConversationId`); not affected, but worth knowing when COS changes.
